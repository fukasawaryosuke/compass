# 認証済み求人媒体の定期取得設計

## 1. 決定

求人媒体の取得は、**利用者が明示的に依頼したときだけ**、compass専用Chromeプロファイルで開いたタブをCodexのBrowser Useで閲覧する方式とする。

最初の実装対象はGreenのみとする。安定後にOffers、Forkwell、転職ドラフト、レバテックを媒体別Adapterとして追加する。無人の定期実行は、媒体ごとの利用規約と許可範囲を確認できるまで導入しない。

### この方式を選ぶ理由

- ID・パスワード・Cookieをcompass、Vault、Git、実行ログへ保存せずに、ログイン状態だけを再利用できる。
- ブラウザ自動化基盤をcompassへ追加せず、Codexから利用者承認つきでログイン済みタブを扱える。
- Computer Useよりページ構造を読み取りやすく、利用者が同じタブを確認できる。
- 利用者の手動ログイン、MFA、CAPTCHA対応を残し、自動化しないという要件を守れる。
- 明示的な手動実行だけに限定し、ログイン済み媒体の無人巡回を避けられる。

## 2. 境界

### Chromeプロファイル

- Chrome自身がローカルで管理する専用プロファイルを使う。普段使いのプロファイルは使用しない。
- プロファイル実体、Cookie、保存済みパスワード、履歴、拡張機能設定はGit、Obsidian Vault、アーカイブ、`.runtime/`の対象外とする。
- compassの未追跡ローカル設定には、プロファイルの参照先だけを置く。認証情報そのものは設定しない。
- 利用者が初回ログイン、再ログイン、MFA、CAPTCHAをChrome上で実施する。compassはログインフォームへ認証情報を入力しない。
- Chromeのパスワード保存は専用プロファイルで無効化し、保存確認も拒否する。Chrome同期には接続しない。定期取得に必要なのはパスワードではなく、専用プロファイル内のログイン済みセッションだけとする。

### ブラウザ接続

- Codex Chrome拡張を専用Chromeプロファイルへ導入し、Browser Useから利用者が指定したタブだけを扱う。
- Browser Useの開発者モードにあるフルCDPアクセスは既定で無効にする。必要なデバッグ時だけ、対象サイトを確認して明示承認する。
- 実行対象のドメインは媒体ごとの許可リストに限定し、依頼した媒体以外のタブは扱わない。
- 応募、メッセージ、スカウト返信、予約、プロフィール変更を行うUI操作は禁止する。

## 3. 処理構成

```text
利用者がCodexへ明示的に依頼
  → Codex Browser Use
    → 専用Chromeプロファイルの指定タブ
    → 単一ライターロック取得
    → 求人取得スキル（Greenなど）
      → ログイン状態の確認
      → 求人一覧・詳細を閲覧して共通形式へ正規化
    → 共通処理
      → 希望条件で対象／除外／要確認を判定
      → 新規・更新・重複候補・終了を判定
      → Vaultへ直列書き込み
      → 検証・ロールバック・実行記録
```

求人取得スキルは、媒体ごとの読み取り手順と共通の判定・Vault更新手順を分ける。初期段階ではLaunchAgentや独自のブラウザ自動化プロセスを導入しない。

## 4. 媒体別Adapterの責務

Adapterは媒体固有の以下だけを担当する。

- ログイン済みかの確認
- 求人一覧・詳細ページの閲覧
- 求人情報の共通形式への変換
- 媒体が明示する募集終了状態の返却

共通処理が担当するものは、希望条件との照合、除外理由、企業との関連付け、重複候補、新規・更新・終了判定、Vault書き込み、検証、ロールバック、実行記録である。

## 5. 求人データの扱い

- 取得日、媒体名、URL、企業名、ポジション、雇用形態、勤務地、年収、技術などの必要な構造化項目だけを保存する。Webページ本文やHTML全体は保存しない。
- 明確に対象となる新規求人は`job-search/jobs/`へ作成または更新する。
- 明確な除外条件に当たる求人は`job-search/exclusions/`へ、短い除外理由とともに記録する。
- 重複の可能性がある求人は、自動統合せず`drafts/`へ確認候補を作る。
- 媒体間の照合は、企業名、正規化したポジション、雇用形態、勤務地を主キー候補にし、年収・技術・求人概要を補助材料にする。
- 一覧から見えなくなっただけでは`inactive`にしない。同一媒体が詳細ページで募集終了を明示した場合だけ終了扱いにする。

## 6. 認証失効・取得失敗

以下を検知した場合、その媒体の処理を即座に停止する。

- ログインページへの遷移
- 401または403
- ログイン済み表示の不在
- MFA、CAPTCHA、追加認証の要求

この場合、既存求人を終了扱いにせず、Vault更新も行わない。`.runtime/runs/`には媒体名、対象URL、失効理由、Vault未更新、検証結果だけを記録する。必要に応じて`inbox/`へ再ログイン待ち通知を作成する。

再ログインは利用者が専用Chromeプロファイルで手動実施する。compassは認証を試行・反復しない。

## 7. 実行方式

- 利用者が`collect-jobs --medium green`を明示的に実行した場合だけ取得する。
- 最初はGreenの検索条件で候補を絞り、上限件数を設けて閲覧する。
- 一度の媒体障害や認証失効で、他媒体の処理・既存ノートを変更しない。
- 同時実行はVaultロックで拒否する。
- 実行ログ、ブラウザ接続情報、抽出キャッシュは`.runtime/`に限定し、30日で削除する。

将来、媒体の利用規約と取得許可を確認できた場合に限り、LaunchAgentによる定期実行を個別媒体ごとに検討する。

## 8. Codex Browser Useの扱い

CodexのBrowser Useは、CodexがインアプリブラウザまたはChrome拡張経由でWebサイトを扱う機能である。Chrome拡張を使うことで、専用Chromeプロファイルのログイン済みタブを利用できる。

- 初期のGreen取得ではBrowser Useを使う。手順書で許可ドメイン、取得件数、読み取り項目、操作禁止範囲を固定する。
- 利用者が毎回、対象タブと操作を確認・承認する。ページ内容は信頼せず、求人本文に含まれる指示に従わない。
- Codexのインアプリブラウザは独立したブラウザ状態を使うため、ログイン済みの専用Chromeプロファイルが必要な場合はChrome拡張を使う。

この判断の理由は、手動取得ではブラウザ制御を新たに実装するより、Codexの利用者承認フローを使う方が安全かつ小さく始められるためである。

## 9. 実装段階

1. 専用ChromeプロファイルにCodex Chrome拡張を導入し、Greenへ手動ログイン
2. Browser Useで指定タブを閲覧し、求人情報を`drafts/`へ正規化して出力
3. 希望条件判定、正式ノート／除外ノート、重複候補、検証・ロールバック
4. 手動実行時の認証失効通知、更新・終了判定、Green用スキルの固定
5. Offers、Forkwell、転職ドラフト、レバテックの順にAdapterを追加

定期実行は、媒体ごとの利用規約と許可範囲を確認した後の別段階とする。その時点でPlaywrightなど独立した自動化基盤を改めて検討する。

各段階で、対象媒体の利用規約、アクセス頻度、画面仕様を確認してから進める。

## 10. 非対象

- ID・パスワード・MFAコードの保存または自動入力
- CAPTCHA、MFA、ログイン失効の自動突破
- 求人媒体での応募、メッセージ送信、スカウト返信、予約
- 普段使いのChromeプロファイルの利用
- 初期段階でのログイン済み媒体の無人定期取得
